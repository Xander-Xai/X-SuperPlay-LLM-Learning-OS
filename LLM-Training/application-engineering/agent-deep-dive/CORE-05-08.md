## 模块 5：企业级 Agent 工程

### 1. API → Runtime → 工具 → 状态的一条链

~~~mermaid
flowchart TB
    Client[Web/App] --> API[FastAPI: Auth/Rate-limit/Request ID]
    API --> Runtime[Agent Runtime: route/plan/execute/stop]
    Runtime --> SSE[SSE progress/event feed]
    Runtime --> Queue[Task queue: long-running jobs]
    Queue --> Worker[Worker with retries and leases]
    Runtime --> Gateway[Tool Gateway: Schema/ACL/HITL/Idempotency]
    Worker --> Gateway
    Gateway --> Biz[PostgreSQL: business transaction]
    Runtime --> Checkpoint[Checkpoint: graph state]
    Worker --> Checkpoint
    Runtime --> Cache[Redis: cache/session/lease]
    Worker --> Trace[Trace/Metric/Error spans]
    Gateway --> Trace
~~~

- **API 层**：认证可信身份，输入 Schema、限流/超时，返回稳定 run_id。客户端自报 role 不能作为真实身份。
- **SSE**：单向事件传输与用户体验；断流后可凭 run_id 查询状态；不是 Durable Queue 或 Exactly Once 保证。
- **任务队列**：长事务交给 Worker（可用 Celery 等）；队列可能至少一次投递，业务工具不能依赖「只调用一次」假设。
- **PostgreSQL**：业务订单、审批、操作记录及必要事务；同一实例也可承载不同逻辑数据库或 Checkpoint 表，但概念边界必须清晰。
- **Redis**：高速缓存、租约/Session/幂等辅助；默认不要把易失内存当唯一可追溯业务真相。
- **Checkpoint**：恢复图状态；不自动保护数据库外部副作用；恢复前后需要业务终态确认。
- **Tracing**：run_id、thread_id、trace_id、tool_call_id 贯通 API/Node/Tool/DB；日志脱敏、审计操作原因。

### 2. 幂等、重试与「至少一次」的难题

客户端超时 → Worker 的退款请求可能已经提交 → 还没返回 HTTP 确认 → 重试可能发生重复退款。安全处理：

1. 为事务分配由**可信后端**构造并绑定 tenant/actor/order/operation 的业务幂等键；
2. 写入前检查 Payload 指纹和状态，受事务锁/唯一约束保护；同键同 Payload 复用已知结果，同键不同 Payload 拒绝；
3. 未知结果不能假定失败；优先按 request_id 查询外部执行状态；必要时人工处理或补偿；
4. 日志记录前后业务状态与重试次数，分别统计「防重复」与「真实退款成功」；
5. 测试 **写前失败、写后回执丢失、恢复重放、重复投递、并行争抢**，只有真实测试数据库才能证明事务边界。

### 3. 容错、并发、性能与运维

| 方向 | 细节 | 示例问题 |
|---|---|---|
| asyncio/并发 | I/O 协程/线程、模型配额、每租户并发资源池 | 25 并发时哪里排队？ |
| 重试与熔断 | 指数退避+随机抖动、错误分桶、熔断与降级 | 哪些写操作绝不可盲重试？ |
| 任务恢复 | DLQ、重放、租约超时、心跳、取消、补偿 | Worker 重启丢失了哪些状态？ |
| 端到端延迟 | P50/P95、TTFT、Tool 等待、队列等待、响应传输 | P95 高是模型还是 Queue？ |
| 资源与成本 | 模型 Token、网络、检索、工具调用、失败任务成本 | 便宜模型为何任务更贵？ |
| 部署/回滚 | Docker、配置版本、灰度、健康检查、日志脱敏 | 发布新 Prompt 后如何回滚？ |

## 模块 6：评测、可观测性、安全

### 1. 三层评测，不用一个模糊的准确率

| 层 | 衡量什么 | 分母/核验 |
|---|---|---|
| Final | 用户任务达成/正确拒绝、回答证据支持 | 对应 task 集、明确拒绝集，使用最终业务状态核对 |
| Trajectory | 路由/工具名/参数/顺序、重复/循环、Handoff、成本 | 需要此工具或决策的案例数 |
| Environment | DB/文件/外部系统状态，安全越权，故障恢复 | 真实执行并触发相应错误/安全用例数 |

关键指标：Task Success Rate、Tool Call Accuracy（Name 和 Args 分开）、Routing Accuracy、Trajectory Quality、Recovery Rate、Safety Violation Rate、Latency P95、Cost per Task。P95 需要说明样本数、时间范围、采样口径，不能把失败和超时全部删掉。拒答用例要区分策略正确拒绝与错误拒答。

**示例**：Agent 说「退款成功」，但订单状态仍为 paid → Final Text 看似成功，业务 Task Success = FAIL。

### 2. Trace 的最小字段

run_id / trace_id / thread_id / actor 的脱敏标识 / prompt+tool schema 版本 / 选中节点 / 工具名和参数摘要 / 调用耗时 / 模型用量/费用 / 结果状态 / 失败分桶 / 业务终态 / 测试用例 ID。敏感文本不应原样写入公共仓库或外发监控。

### 3. 主要安全威胁

- **Prompt Injection**：网页、检索文档或 Tool Output 是低信任数据，不因写了「系统指令」就提权。
- **Excessive Agency**：工具范围过大、可写系统缺少审批。
- **数据泄露**：跨租户工具/记忆、日志脱敏不足。
- **供应链/沙箱**：不可信代码执行、依赖和工具服务器。
- **错误结果声明**：工具调用失败被包装为完成；错误拒答被混入正确结果。

同时执行输入检查、执行层 IAM/ACL、审批、隔离、输出事实校验、审计与人工兜底；Prompt 是辅助防线，不能单独保障敏感操作。

来源：[Anthropic Agent Evals](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)、[LangSmith Evaluate Graph](https://docs.langchain.com/langsmith/evaluate-graph)、[OWASP Agentic Applications](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026/)。

## 模块 7：MCP、Agent Skills、A2A、Harness

### 1. 协议/封装层的职责

| 对象 | 它是什么 | 它不是什么 |
|---|---|---|
| MCP | AI Host/Client 与 Server 在 Tools/Resources/Prompts 等方面的标准化连接协议 | 不自动等于企业 IAM、审批与数据边界 |
| Function Calling | 模型输出符合工具调用结构的意图 | 不代表 Tool Server 已授权并执行 |
| Skills | 以 SKILL.md 为核心的按需加载指令/参考资料/脚本组合 | 不是工具调用协议或后端沙箱 |
| A2A | 独立 Agent 应用之间任务与消息互操作协议 | 不是本地调用 Python 子 Agent 的必要条件 |
| Harness | 任务循环、Context、工具执行、预算、状态、隔离、恢复、Trace 和验收机制集合 | 不等于只装 MCP 或只写 Prompt |

**Computer Use（P2）**：模型看到桌面/浏览器界面，提出截图、点击、键盘操作，工具由宿主在沙箱实际执行并观察结果；网页内容仍是低信任输入。不要授予访问真实账户、任意文件或敏感凭据的默认权限。它并不意味着使用 MCP，也不代替授权和动作审计。官方参考：[Anthropic Computer Use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool) · [OpenAI Computer Use](https://developers.openai.com/api/docs/guides/tools-computer-use)。

### 2. MCP 与 A2A 的数据流

MCP：AI 应用 Host ↔ Client ↔ Tool/Data Server。Host 需要根据可信身份控制可用能力；Server 的返回仍是低信任资料。真正操作要在服务端授权。

A2A：独立 Agent A ↔ 独立 Agent B 的互操作，涉及能力发现、任务生命周期、消息/产物、异步/流式；可以和 MCP 组合，但学习初期不必实现分布式 A2A。

Skills：一个 Skill 至少包含 SKILL.md，可附 scripts/references/assets。加载说明不等于直接执行任意脚本，执行权限由宿主决定。

### 3. Harness 五个学习重点

- **Runtime loop 与终止**：max turns / time / tool budget，区分任务继续、停止与失败。
- **Context 预算**：上下文压缩和按需重载；不把记录的全部内容无差别塞给模型。
- **Workspace/Sandbox**：最小化工具权限，文件/进程/网络隔离。
- **Progress/Durable**：跨阶段留下完成证据，中断后能核对已做和未做的副作用。
- **Eval/Review**：任务级结果和 Trace 可复现；长任务必须校验实际文件/网页状态。

来源：[MCP 规范](https://modelcontextprotocol.io/specification/)、[Agent Skills 规范](https://agentskills.io/specification)、[A2A](https://a2a-protocol.org/latest/)、[长任务 Harness 实践](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)（具体页面会随发布迁移，使用前核对来源）。

## 模块 8：综合交付与面试

### 1. 四种能力的交付证据

| 能力 | 目标 | 证明材料 |
|---|---|---|
| 原理 | 无框架画出循环与消息协议 | Mini Loop、闭卷讲解 |
| 开发 | 从需求到 API/Tool/State 的可运行系统 | 带版本的代码和测试 |
| 架构 | 单次 LLM、Workflow、单 Agent、多 Agent 的取舍 | 固定集消融、成功/成本数据 |
| 工程 | 可靠性、Tracing、安全、故障根因、发布/回滚 | 故障注入 Trace、业务终态、G0–G8 |

### 2. 从既有多智能体客服项目穿透式复盘

以「查询订单并申请退款」为锚：身份在哪里验证？订单查询和知识检索何时调用？Router 与 Supervisor 如何选？审批如何暂停/恢复？Worker 宕机后如何避免重复退款？Trace 如何贯通？哪个失败是模型选错，哪个是工具 API 超时，哪个是 ACL 拒绝？最终用户文案与 DB 状态是否一致？

### 3. 面试最低验收

- 白板 10 分钟：画出完整时序图、状态与 DB 的区别；
- 现场 15 分钟：解释一个含 tool_call_id 和错误的 Trace；
- 现场 20 分钟：修改/复现未知故障，并用测试证明；
- 实验报告：固定任务集对比 Workflow / 单 Agent / 多 Agent，报告成功率、拒答、成本、P95、安全；
- 真实生产上线如在范围内，另按照 G0–G8；课程完成并不默认投产。

优先用 [原有 24 道 Agent 面试题](../AGENT-INTERVIEW-QUESTIONS.md)，新增问题不重造一套冲突题库。关于个人能力判分，遵守 [统一 Rubric](../../assessments/CAPABILITY-RUBRIC.md)。

**结论**：目标是「能解释、能实现、能诊断、能取舍」，而非刷完框架文档。按照实际任务达标即停止。
