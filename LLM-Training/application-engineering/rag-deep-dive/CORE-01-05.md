## R01｜适用边界、检索增强的本质

- **专业**：在生成推理时注入可检索的非参数化证据；经典 RAG 论文讨论参数化 Seq2Seq 与稠密 Wikipedia 检索的结合。现代企业系统通常扩展为索引、权限、版本、检索、重排、Context、生成和评估的模块化流水线。
- **白话**：模型不是万能的背书员，而是先找获准且有效的文件，再据此答题。
- **何时不用**：订单余额/库存等权威结构化实时值先用 SQL/API；短文档允许直读时对照 Long Context；高频固定问题可用 FAQ/规则。
- **验收**：闭卷绘制在线+离线链路，解释 SFT 与 RAG 的更新机制与缺点；为三个场景选择 RAG / SQL / 长上下文，并列成本与可靠性指标。
- **失败例**：检索到已废止法规却无生效期过滤；给检索上下文加“仅用证据”Prompt 但服务端未做 ACL。
- **主来源**：[RAG 原始论文](https://arxiv.org/abs/2005.11401)、[LangChain Retrieval](https://docs.langchain.com/oss/python/langchain/retrieval)。

## R02｜解析、OCR、表格、Chunk 与可追溯性

**输入**：PDF、DOCX、HTML、Excel、照片、扫描法规。**过程**：合法采集→文档类型判定→文字/OCR/版面/表格结构→去重/页眉页脚噪声→标题层级→Chunk（含重叠或父子块）→metadata→原文/索引一致写入。**输出**：可追溯的 chunk_id、document_id、source_uri、page、section、tenant、ACL、version、valid_from/to、parser_version、content_hash、parent_id。

Chunk 策略与代价：
1. 固定长度 256/512/1024 token：快、可控，但会拆断公式、表格行、定义与例外。
2. 递归/标题/段落：尊重结构，仍可能在跨标题答案上失败。
3. Parent–Child：子块召回、父块扩展；改善局部定位，但上下文/存储/多处合并成本增加。
4. Contextual Retrieval：为块增加所属文档、章节等上下文；有额外索引成本与生成背景失真风险。

**关键细节**：token 与字符数不是一回事；表格需要行列关系及单位；图片需要 OCR 与视觉理解分别评估；不能仅靠 overlap 弥补解析错误。索引删除与重建时，原文、索引、引用页码须指向同一版本。

**实验**：固定相同 Gold 源片段，比较三种 Chunk；同时报 Recall@5/10、平均 context tokens、表格行列准确率、P95、噪声比例。按来源文档/片段 ID 标注 gold，避免 Chunk ID 改变后测量基准漂移。

**负例**：否定词跨 Chunk、表头丢失导致浓度单位反转、扫描 OCR 将产品编号 0/O 混淆、页码漂移。

**主来源**：[Docling 官方项目](https://github.com/docling-project/docling)、[Anthropic Contextual Retrieval](https://www.anthropic.com/research/contextual-retrieval)。

## R03｜Embedding、表示学习与选型

**数据流**：Tokenizer → Transformer Encoder → token pooling（CLS/Mean 等，必须看模型说明）→可选 L2 归一化→文档/查询向量→Cosine / Dot / L2。

- Cosine：夹角，不关心向量长度；归一化向量上 Dot 与 Cosine 相同，平方 L2 与 Cosine 成单调关系（在相同归一化条件下）。
- BiEncoder：分别编码 Query/Document，适合预编码文档与 ANN 搜索；CrossEncoder：联合编码 Query + 候选，适合少量精排。
- Hard Negative：与 Query 相似却不相关的负例；训练时可提升判别，但错误负标注会造成训练偏差。
- BGE-base-zh-v1.5 与 BGE-M3：模型维度、语言、最大长度、稀疏/多向量能力需看各自官方卡片；**不同维度/向量空间不得直接混用**。换 Embedding 通常要按索引版本重算向量。
- 避免纯凭 MTEB 总分决策：企业产品型号、法规文种、中文别名、成本与响应时延才是自己 Gold Set 的权威对照。

**实验**：冻结 Chunk、Query、ACL、Top-K 和 ANN 精度，比较 BGE 各模型；另外固定 Embedding 只比较 cosine/dot 的归一化影响。输出模型版本、维数、召回率和吞吐。**本仓离线微实验不含真向量模型**。

**主来源**：[BGE-M3 Model Card](https://huggingface.co/BAAI/bge-m3)、[Sentence Transformers Retrieve & Re-Rank](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)。

## R04｜BM25 / Dense / ANN / Hybrid

**BM25（经典变体）**：
~~~text
score(q,d) = Σ[t∈q] IDF(t) * (tf(t,d)*(k1+1))/(tf(t,d)+k1*(1-b+b*|d|/avgdl))
IDF(t) = ln(1 + (N-df(t)+0.5)/(df(t)+0.5))
~~~
其中 tf 为词频、df 为包含词的文档数、|d| 为文档长度。它依赖语言分词策略，不等于精确子串检索。适合编号、术语和词项匹配；不能天然泛化所有同义词。

**Dense**：编码成向量，能发现语义相似；可能错过产品编码、极少见术语或否定条件。**Hybrid**：两路先分别高召回，再去重/融合，不能混加尺度不同的 BM25 与向量原始得分。

**ANN**：FLAT 精确距离扫描（作真值对照）、HNSW 图搜索（M、efConstruction、efSearch）与 IVF 分桶（nlist、nprobe）。逐一评估 Approx Recall 相对 FLAT、索引大小、构建耗时、延迟及并发；ANN 不是必然比 FLAT 更准确。**ACL/版本过滤要在候选生成前或引擎可信过滤路径落实**，融合及读取正文阶段二次防御。

**负例**：精确的法规代码被向量同义内容挤走；检索全库后过滤导致 Top-K 无有效授权证据；修改 HNSW efSearch 后延迟上升但 Recall 增益极少。

**主来源**：[斯坦福 IR 教科书](https://www-nlp.stanford.edu/IR-book/)、[Milvus Index Explained](https://milvus.io/docs/index-explained.md)、[Elastic Hybrid Search](https://www.elastic.co/docs/solutions/search/hybrid-search)。

## R05｜融合、重排与候选裁剪

**RRF**：对每个来源返回的候选按 1 起始的名次 r 计分，score(d)=Σ 1/(k+r)。只依赖名次，分数尺度无需统一；但候选集合过小、跨列表重复内容、结果次序变化都可能影响融合结果。k 是排名平滑常数，非 Top-K 的 K。

**两阶段检索**：BM25 + BiEncoder/Dense 各取 Top-N → 权限/去重 → RRF → CrossEncoder 联合 Query/Doc 精排 → 截断到 context budget → 证据门禁。CrossEncoder 的相对优势与成本必须在固定候选集下测；不是所有架构都要再串一个 BiEncoder 精排。

**实验**：固定两路候选，手算两个文档 RRF；比较 Dense-only / BM25-only / RRF / RRF+CrossEncoder 的 MRR、nDCG、Recall、P95 与成本。注意金标可能是多个片段，不应把含一个正确片段的 Hit@5 当全覆盖。

**负例**：只有一路高价值的文档被双路普通候选排在后面；若过滤前融合，未授权文档占用候选数；文档重复导致上下文拥挤。

**主来源**：[Elastic RRF](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)、[Sentence Transformers](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)。
